WHY
  Review of 10g (Claude, 2026-11-24) found three problems:

  1. Every poll takes the database write lock. prune_change_log runs
     BEGIN IMMEDIATE BEFORE it checks the once-per-hour gate, so every
     labeled/changes call (every 15 s per open tab) competes for the
     write lock with the LLM worker, the Zotero sync and saves.
     Measured on a copy of a real project (scratch, 2026-11-24): with
     another connection holding the write lock, opening the Database,
     get_project_state and get_changes_since each take 0 ms, and
     prune_change_log fails with "database is locked" after 5.2 s
     (sqlite3's default 5 s busy timeout). So a long write (bulk
     relabel, import) makes polls fail.
  2. prune_change_log does not guard against an open transaction. If
     the connection is already in a transaction, BEGIN IMMEDIATE raises
     "cannot start a transaction within a transaction". Safe in the
     endpoint today (the prune is the first statement on a fresh
     Database), but not for any other caller.
  3. Many cases of test_ids_equal_concatenated_pages check nothing:
     with 15 relevant / 15 irrelevant / 10 notes at per_page=7,
     relevant, irrelevant and every has_note case run out of rows
     before page 3 (boundary is always "end"); unlabeled + has_note has
     no matches at all; no record has a PDF, so pdf=false returns the
     same rows as no filter. Measured with an injected bug (labeled/ids
     ignoring the pdf filter): none of the 24 matrix cases fail; only
     the final "every loaded row leaves" block catches it.

  The user decided: fix all three in a follow-up task.
  Proposed by Claude and confirmed by the user (2026-11-24):
  - An open transaction makes prune_change_log RAISE, not commit. A
    silent commit would commit someone else's half-done work.
  - A busy database (SQLITE_BUSY) while pruning is logged and ignored
    by the endpoint: change_log is a debugging history, so pruning must
    never fail a poll. Any other error still propagates.

    commits and returns the deleted count. rollback on BaseException.
  - The connection uses Python's legacy transaction control (default
    isolation_level): a plain SELECT does not open a transaction;
    INSERT/UPDATE/DELETE do (con.in_transaction becomes True).
  - Opening a read-write Database (open_db) does NOT need the write
    lock: its CREATE ... IF NOT EXISTS statements are no-ops on an
    existing schema and succeed while another connection holds the
    lock (measured).
  - sqlite3.OperationalError carries e.sqlite_errorcode (Python 3.11+).
    It is the EXTENDED result code: a duplicate primary key gives 1555
    (SQLITE_CONSTRAINT_PRIMARYKEY), not 19. The busy variants are
    SQLITE_BUSY 5, SQLITE_BUSY_RECOVERY 261, SQLITE_BUSY_SNAPSHOT 517
    and SQLITE_BUSY_TIMEOUT 773; all are sqlite3 module constants. The
    low byte (code & 0xFF) is the primary code, so all four give 5. The
    busy-timeout case measured on 2026-11-24 gave exactly 5. The
    attribute is writable on a hand-made exception, so a test can build
    one:

        e.sqlite_errorcode = sqlite3.SQLITE_BUSY

     def _prune_due(self, now, min_interval_s):
         """Whether pruning is due: never pruned, or the last prune is
         at least ``min_interval_s`` old. A plain read; takes no write
         lock."""
         row = self._conn.execute(
             "SELECT last_pruned_at FROM project_state"
         ).fetchone()
         last_pruned_at = row[0] if row is not None else None
         return last_pruned_at is None or now - last_pruned_at >= min_interval_s

  2. prune_change_log becomes (same signature, same return value):

        if now is None:
            now = time.time()
        con = self._conn
        if con.in_transaction:
            raise RuntimeError(
                "prune_change_log() must not run inside an open transaction"

SPEC NOTE (append at the END of specs/0001-collection-snapshot.md)
------------------------------------------------------------------------
  ### Polls never take the write lock for pruning (10g2, 2026-11-24)

  `prune_change_log` checks the hourly gate with a plain read first and
  takes the write lock (`BEGIN IMMEDIATE`, then checks again) only when
  pruning is due. A busy database while pruning is logged and ignored by
  `labeled/changes`, so pruning never fails a poll. It raises
  `RuntimeError` inside an open transaction instead of committing the
  caller's work. Measured before the fix: with another writer holding
  the lock, every poll failed with "database is locked" after 5.2 s.
