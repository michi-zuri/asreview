WHY
  Two version numbers are visible to upstream ASReview, and both are
  currently 4. Upstream is at 3, so 4 reads like "upstream version 4",
  and upstream handles it badly:
  - project.json "project_file_version": 4. Upstream's Project.load only
    migrates when the version is < 3 and has no "too new" check, so it
    copies a fork project into its projects folder and the webapp import
    reports success.
  - results.db PRAGMA user_version = 4. Upstream fails its version check
    when it opens the database, then calls create_tables() on the existing
    file, which rewrites user_version to 3 before crashing. A future
    upstream v4 would accept 4.

  The user decided:
  - project.json "project_file_version" = -1, meaning "asmr project; its
    schema state is in the ledger". Upstream then calls
    migrate_project(tmpdir, -1, 3), whose first guard
    `if src_version < 1: raise ValueError(...)` fires BEFORE the copy:
    the import is refused and nothing reaches the projects folder.
  - -1 is also the fork's own target. Project.VERSION becomes -1. The
    4 was never an upstream version: it labelled the end of the fork's
    step "upstream v3 → fork". That step stays (it converts upstream
    projects), but its target is now "asmr", not a number. The chain is
    1 → 2 → 3 → asmr, walked through a next-version table instead of
    `+= 1`, and the integer comparisons (`< Project.VERSION` = "needs
    migration") become two helpers. A fork project never migrates at
    project level again: every later change, to results.db or to files
    beside it, is a ledger revision (as 0000 already is).
  - A plain 4 on disk is a legacy fork project (all 15 local projects,
    the deployment, old exports). It gets a small step 4 → asmr: refuse
    unless results.db carries the asmr mark (an unmarked 4 is a future
    upstream project), then write -1. So `asreview migrate --projects`,
    the webapp upgrade route and import convert them; no manual script.
  - results.db user_version = 0x61736D72 (1634954610, the same value as
    the application_id mark; it fits SQLite's signed 32-bit
    user_version). No upstream release will ever match it.

  Upstream files keep their own numbers: migration still recognises an
  upstream v3 project by project_file_version 3 and an upstream v3
  database by user_version 3. Only the fork's OWN files change.

DESIGN (decided — follow it)
  fork_migrations.py (home of the fork identity constants)
    - ASMR_PROJECT_VERSION = -1, with a comment: the fork's project file
      version and the end of the migration chain; upstream's
      migrate_project raises for it before copying a project in.
    - FORK_USER_VERSION = FORK_APPLICATION_ID, with a comment: no
      upstream release's database version check ever matches it.
    - LEGACY_FORK_USER_VERSION = 4 (what 10d2 and earlier wrote).
    - New revision, appended to REVISIONS:
          def _rev_0002_user_version_mark(cur, ctx):
              cur.execute(f"PRAGMA user_version = {FORK_USER_VERSION}")
      user_version lives in the file header and is transactional, so it
      commits or rolls back with the ledger's BEGIN IMMEDIATE.
    - BASELINE_REVISIONS = ("0000_tags_tables", "0002_user_version_mark").
    - Module docstring: user_version holds the mark; schema state is the
      ledger.

  migrate.py
    - UPSTREAM_VERSIONS = (1, 2, 3).

      4: ASMR_PROJECT_VERSION}, with a comment that 4 is a legacy fork
      project.json.
    - def needs_migration(version): return version in NEXT_VERSION
    - def is_supported_version(version):
          return version == ASMR_PROJECT_VERSION or needs_migration(version)

      -1 in the docstring.
    - migrate_project(folder, src_version, dst_version=ASMR_PROJECT_VERSION):
      guards: not needs_migration(src_version) → ValueError("Project
      version {src} cannot be migrated."); dst_version !=
      ASMR_PROJECT_VERSION → ValueError. Loop
          while current_version != dst_version:
              _migrate_project_one_version(folder, current_version)
              current_version = NEXT_VERSION[current_version]
      Keep the empty-v1/v2 handling and the exception wrapping.
