WHY
  Upstream ASReview is at project/database version 3. This fork ("asmr",
  automated systematic mapping review) uses 4, and a future upstream v4
  would carry the same number with a different schema. From now on:
    - a fork database carries PRAGMA application_id = 0x61736D72
      (the bytes b"asmr", decimal 1634954610). That is THE fork mark.
    - an upstream v3 project (project_file_version 3, user_version 3,
      no mark) is upgraded to the fork. The schema part of today's
      v3→v4 migration becomes ledger revision "0000_tags_tables".
    - any other database without the mark is REFUSED (future upstream
      v4, v5+, anything foreign). There is NO detection of old fork
      databases without the mark: the user marks their existing
      deployments by hand before deploying this.
  Ledger id "0001_change_tracking" must stay as it is: real databases
  already have that row.

DESIGN (decided — follow it)
  1. fork_migrations.py
     - `FORK_APPLICATION_ID = 0x61736D72  # b"asmr"`
     - `BASELINE_REVISIONS = ("0000_tags_tables",)`: revisions whose
       result create_tables() already builds directly.
     - New `def mark_fork_database(conn):` sets
       `PRAGMA application_id = {FORK_APPLICATION_ID}`, creates the
       ledger table if missing, INSERT OR IGNORE the BASELINE_REVISIONS
       rows (applied_at = time.time()), commit. Called by create_tables
       only.
     - Revision functions take (cur, ctx). `ctx` is a small dataclass
       `MigrationContext(project_id: str, project_path: Path | None)`;
       project_path is the folder holding results.db, None in memory.
       Change `_rev_0001_change_tracking` to read ctx.project_id.
       `apply_fork_migrations(conn, project_id, project_path=None)`.
     - REVISIONS = [("0000_tags_tables", _rev_0000_tags_tables),
                    ("0001_change_tracking", _rev_0001_change_tracking)]
     - `_rev_0000_tags_tables(cur, ctx)` calls
       `v3v4.migrate_db(cur, ctx.project_path)` (local import inside
       the function; see 2). Guard FIRST: if the `tag_options` table
       already exists, raise RuntimeError("0000_tags_tables on a
       database that already has the v4 tag schema; is the
       '0000_tags_tables' ledger row missing?"). That turns a missing
       ledger row into a rollback instead of a corrupted database.
     - File cleanup (deleting tags.json/lists.json) must happen only
       AFTER the ledger commit. Let a revision return a list of
       callables; apply_fork_migrations calls them after commit().

  2. v3v4.py (stays self-contained)
     - Split `_migrate` into:
         `migrate_db(cur, project)`: the schema rewrite, steps 1–11, on
         the GIVEN cursor, with NO commit anywhere (remove the commits,
         including in _rebuild_results_without_tags). SQLite DDL is
         transactional, so the ledger's BEGIN IMMEDIATE covers it. It
         sets `PRAGMA user_version = 4` and returns the cleanup
         callables that delete tags.json/lists.json.
         `_migrate(project)`: project.json project_file_version = 4;
         open results.db with sqlite3; check user_version == 3 and
         application_id == 0 (else raise ValueError naming both);
         `PRAGMA application_id = FORK_APPLICATION_ID`; then
         `apply_fork_migrations(conn, Path(project).name, project)`
         (local import from asreview.database.fork_migrations — that
         module imports only stdlib, so the self-contained rule holds),
         which applies 0000 and 0001; close.
     - `_validate` keeps checking project_file_version == 4 and
       `_is_valid(expected_version=4)`; that now also requires the
       mark (see 3).
     - Keep its docstring's change list; add "PRAGMA application_id is
       set to the asmr mark" and "the schema rewrite is ledger revision
       0000_tags_tables".

  3. database.py
     - create_tables(): after setting user_version, call
       `mark_fork_database(self._conn)` (before creating the tables).
       The last line stays self._apply_fork_migrations(), which now
       applies only 0001 on a new database.
     - _apply_fork_migrations(): pass project_path
       (`None if self._in_memory else Path(self.fp).parent`).
     - _is_valid(): FIRST check (before user_version):
           app_id = PRAGMA application_id
           if app_id != FORK_APPLICATION_ID: raise ForeignDatabaseError(
               f"{self.fp} is not an asmr database (application_id "
               f"{app_id}, user_version {self.user_version}). Upstream "
               "v3 projects are upgraded through project migration; "
               "other versions are not supported.")
       `class ForeignDatabaseError(ValueError)` defined in database.py.
     - open_db(): call create_tables() only when the database has no
       tables at all (`SELECT count(*) FROM sqlite_master WHERE
       type='table'` == 0). Otherwise re-raise the ValueError. Read-only
       behaviour stays as it is.

     - migrate_project: `dst_version > 4` check stays. A project with

     - Project.load (asreview/project/api.py ~553): after the migration
