WHY
  Review of 10g (Claude, 2026-11-24), point 2: a silent mismatch in
  get_changes_since. The change-tracking triggers stamp every
  record_versions / change_log row with
  (SELECT project_id FROM project_state): the id stored in the file
  when 0001_change_tracking ran (the folder name at that time). But
  get_changes_since filters on Database.project_id, which is the
  CURRENT folder name. When the two differ, every poll silently
  returns no changes, and no error is raised. Proven on the staged
  code (scratch, 2026-11-24): copy a project folder under a new name,
  open it, label a record → db.project_id == "b",
  get_changes_since(0) == [].
  Nothing in the file enforces the D8 invariant "one project_state row;
  every row carries its id" either: a second project_state row, a
  deleted row or a foreign row are all accepted silently.

  The user decided:
  - The project id mismatch is a major problem; fix it with guardrails.
  - Keep the per-row project_id columns (D8): a later Postgres move
    (Spec 0002 Phase 3) merges the per-project databases and needs them.
  - Phase 0 (this task) makes the id consistent INSIDE one database
    file. Checking the file's id against the folder name, project.json
    and the auth DB is Phase 1 of Spec 0002, NOT this task.

CHANGE 1 (asreview/database/fork_migrations.py)
------------------------------------------------------------------------
  New revision, placed after _rev_0003_record_versions_version_idx:

  def _rev_0004_project_id_consistency(cur, ctx):
      """Refuse a database whose change-tracking rows disagree on the
      project id.

      ``project_state`` must hold exactly one row, and every
      ``record_versions`` and ``change_log`` row must carry its
      ``project_id``. From here on the ``trg_pid_*`` triggers (see
      ``Database._ensure_change_tracking_triggers``) keep it that way.
      Raising rolls back the whole migration run, so the database stays
      as it was.
      """
      n_state = cur.execute("SELECT COUNT(*) FROM project_state").fetchone()[0]
      if n_state != 1:
          raise RuntimeError(
              f"project_state holds {n_state} rows; expected exactly one"
          )
      for table in ("record_versions", "change_log"):
          n_foreign = cur.execute(
              f"SELECT COUNT(*) FROM {table} "
              "WHERE project_id IS NOT (SELECT project_id FROM project_state)"
          ).fetchone()[0]
          if n_foreign:
              raise RuntimeError(
                  f"{n_foreign} {table} rows carry a project_id other than "
                  "project_state.project_id"
              )

  Append ("0004_project_id_consistency", _rev_0004_project_id_consistency)
  to REVISIONS. Do NOT add it to BASELINE_REVISIONS: on a new database
  it runs right after 0001 and passes trivially.
  It deliberately does NOT repair anything: an inconsistent file is a
  bug to look at, not to paper over. (No real project is affected; see
  FACTS.)

  Update the MigrationContext docstring: ``project_id`` is the SEED for
  project_state when 0001 creates it (folder name or "memory"); after
  that the stored row is the only authority.

  rekey_project_id: keep the code. Add a comment above the loop:
  project_state MUST be updated first. Its cascade trigger
  (trg_pid_project_state_cascade) then re-keys record_versions and
  change_log, so the two later UPDATEs match no rows. They stay for
  databases opened before the triggers exist. In the docstring, replace
  "so their rows follow the new id instead of being orphaned" by
  wording that says the guard triggers would refuse any other order.

  c. Replace the project_id property:

     @property
     def project_id(self):
         """The project id stored in ``project_state``.

         The only authority for the id inside this file. None when the
         table or its row does not exist (a new database before
         create_tables, or a read-only open of a database that was
         never migrated).
         """
         con = self._conn
         if con.execute(
             "SELECT 1 FROM sqlite_master "
             "WHERE type='table' AND name='project_state'"
         ).fetchone() is None:
             return None
         row = con.execute("SELECT project_id FROM project_state").fetchone()
         return row[0] if row is not None else None

     New private method below it, used ONLY by _apply_fork_migrations:

     def _seed_project_id(self):
         """The id 0001_change_tracking seeds project_state with: the
         folder name of the database file, or "memory"."""
         if self._in_memory:
             return "memory"
         return Path(self.fp).parent.name

     _apply_fork_migrations passes self._seed_project_id() instead of

  d. _ensure_change_tracking_triggers: add these triggers with the
     existing _add helper, after the trg_ct_* ones and before the
     execute loop. Update the docstring: it also creates the
     project-id guard triggers (Spec 0002 Phase 0).

     _add("trg_pid_project_state_insert",
          "BEFORE INSERT ON project_state",
          "SELECT RAISE(ABORT, 'project_state holds exactly one row');",
          when="EXISTS (SELECT 1 FROM project_state)")
     _add("trg_pid_project_state_delete",
          "BEFORE DELETE ON project_state",
          "SELECT RAISE(ABORT, 'project_state holds exactly one row');")
     _add("trg_pid_project_state_update",
          "BEFORE UPDATE OF project_id ON project_state",
          "SELECT RAISE(ABORT, "
          "'project_state.project_id must be a non-empty string');",
          when="NEW.project_id IS NULL OR NEW.project_id = ''")
     _add("trg_pid_project_state_cascade",
          "AFTER UPDATE OF project_id ON project_state",
          "UPDATE record_versions SET project_id = NEW.project_id; "
          "UPDATE change_log SET project_id = NEW.project_id;",
          when="OLD.project_id IS NOT NEW.project_id")
     for table in ("record_versions", "change_log"):
         for event, suffix in (
             (f"BEFORE INSERT ON {table}", "insert"),
             (f"BEFORE UPDATE OF project_id ON {table}", "update"),
         ):
             _add(f"trg_pid_{table}_{suffix}", event,
                  f"SELECT RAISE(ABORT, "
                  f"'{table}.project_id must equal project_state.project_id');",
                  when="NEW.project_id IS NOT "
                       "(SELECT project_id FROM project_state)")

     Why the cascade passes the row guards: it is an AFTER trigger, so
     project_state already holds the new id when record_versions /
     change_log are updated.
     The trg_ct_* bodies insert with
     SELECT project_id … FROM project_state, so they always pass.

SPEC NOTE (append at the END of specs/0001-collection-snapshot.md)
------------------------------------------------------------------------
  ### One project id per file (10g3, 2026-11-24)

  Supersedes the Q4 answer ("project_state.project_id = folder name,
  informational until a Postgres merge"). The folder name only seeds
  `project_state` when `0001_change_tracking` creates it. After that
  the stored row is the only authority inside the file:
  `Database.project_id` reads it, and `get_changes_since` /
  `get_record_versions` filter with `(SELECT project_id FROM
  project_state)`. The trigger bodies already did this. Before the fix,
  copying a project folder under a new name made every
  `labeled/changes` poll silently empty.
  Guard triggers (`trg_pid_*`, created on every read-write open)
  enforce D8 inside the file: exactly one `project_state` row with a
  non-empty id; every `record_versions` / `change_log` row carries it.
  Changing the id in `project_state` cascades to both tables. Revision
  `0004_project_id_consistency` refuses (and rolls back) a database
  that breaks this before the guards existed. Matching the file's id
  against the folder, `project.json` and the auth database is Spec 0002
  Phase 1.
